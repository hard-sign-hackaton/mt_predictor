# MT Predictor

Текущий интеграционный срез объединяет диспетчерскую карту и read-only очередь прогнозируемых задержек. Backend принимает бинарный NDTP-поток, связывает `unit_id` с вычисленным паттерном маршрута, определяет прохождение остановок, рассчитывает текущую задержку и вызывает ML по gRPC. Прогноз больше 120 секунд превращается в live-инцидент и поступает в React-клиент через SSE.

## Быстрый запуск

Требуются Docker Desktop / Docker Engine с Compose. Контролируемый моковый контур запускается одной командой:

```bash
cd mt_predictor
./demo/start-demo.sh
```

Либо напрямую через Compose:

```bash
docker compose --profile mock up --build -d
```

После запуска:

- карта: <http://localhost:5173>;
- health backend: <http://localhost:8080/health>;
- HTTP/SSE API: `localhost:8080`;
- TCP-приёмник NDTP: `localhost:9201`.
- gRPC ML: `localhost:50051`.

Остановить контур:

```bash
docker compose down
```

По умолчанию скрипт запускает контролируемый мок, а не весь исторический `validate/traffic.csv`. `backend/data/mock_telemetry.csv` содержит 63 валидные GPS-точки одного рейса за почти 15 минут; точки стоянки исключены, скорость в треке варьируется от 10 до 47 км/ч. Feeder воспроизводит их с ускорением `2x` — непрерывный прогон занимает около 7 минут — и после конца не зацикливает трек и не подделывает свежесть остановившегося ТС. Backend использует исходное календарное время для обычного map matching и считает `currentDelaySeconds` по расписанию. На карте видны промежуточные позиции и изменяющаяся скорость. CSV проходит тот же TCP listener и обработку, что и эмулятор. Отдельно загружаются семь детерминированных сценариев причин для проверки очереди инцидентов.

## Что запускается

```text
mock_telemetry.csv -> NDTP feeder --TCP:9201--┐
                                             ├-> decode -> map matching -> currentDelaySeconds
официальный эмулятор -----------TCP:9201-----┘
mock_scenarios.json -> demo endpoint -> predictions/incidents -> HTTP + SSE -> React
```

- `backend` загружает вычисленный каталог маршрутов один раз при старте, слушает NDTP, асинхронно вызывает ML и публикует API карты и инцидентов;
- `ml` загружает CatBoost + Transformer и использует FP32 ONNX Runtime для Transformer-части на CPU;
- `feeder` в профиле `mock` проигрывает почти 15-минутный трек движения за 7 минут, не повторяя его бесконечно;
- `frontend` показывает географическую карту и отдельную вкладку активных инцидентов;
- синтетические train-примеры не попадают в каталог live-карты.

Для контролируемой проверки причин задержек в backend включён отдельный demo-вход сценариев. Он выключен по умолчанию у бинарного сервера и включён только конфигурацией локального Compose.

Плитки OpenStreetMap загружаются из интернета. Без сети сохраняются маршруты, остановки и транспорт, но не базовая подложка.

## Что делает единая команда

```bash
./demo/start-demo.sh
```

Скрипт при необходимости сам загружает образ организаторов, запускает все четыре контейнера, без вывода временных ошибок ждёт готовности Spring API и передаёт конфигурацию пяти тестовых ТС.

Профили источников взаимоисключающие: моковый поток запускается командой `docker compose --profile mock up --build -d`; официальный эмулятор запускается отдельно командой `./demo/start-demo.sh emulator`. Для эмулятора требуется заранее загруженный образ организаторов. Чтобы специально воспроизвести шум исторической выборки (в том числе очень больших вычисленных отклонений), есть профиль `historical-replay`:

```bash
docker compose --profile historical-replay up --build -d
```

## Ручной запуск официального эмулятора

Образ организаторов лежит вне репозитория и сначала загружается вручную:

```bash
docker load -i ../../dataset/ndtp-telemetry-emulator.tar
docker compose --profile official-emulator up -d official-emulator
curl -X POST http://localhost:18080/api/config \
  -H 'Content-Type: application/json' \
  --data-binary @demo/official-emulator-config.json
```

Пример запускает пять ТС (`990000101`, `990000307`, `990000509`, `990000711`, `990000913`) с `autoGenerate: true`. Для каждого ТС официальный эмулятор независимо генерирует случайную телеметрию и раз в секунду отправляет её в `backend:9201`. Выделенный числовой диапазон позволяет сразу отличить тестовые ТС, не добавляя в NDTP несуществующее строковое имя. Последние три цифры специально различаются, чтобы алгоритм `autoGenerate` разносил стартовые позиции по области, а не создавал все пять ТС рядом. Эти ID намеренно отсутствуют в каталоге раздачи, поэтому backend честно помечает их как «ТС не привязано». На Apple Silicon официальный образ запускается через эмуляцию `linux/amd64`, поэтому первый старт занимает несколько секунд.

Если официальный эмулятор запускается отдельной командой Docker, а backend — на хосте, в конфигурации следует использовать `targetHost: "host.docker.internal"`.

## Контракты карты

| Ресурс | Назначение |
|---|---|
| `GET /api/v1/map/init` | Статические остановки, геометрии route pattern, рейсы и реальные привязки `unit_id -> tr_id` |
| `GET /api/v1/map/snapshot` | Последнее согласованное состояние всех принятых ТС |
| `GET /api/v1/dashboard/snapshot` | Согласованный снимок ТС, последних прогнозов и активных инцидентов |
| `GET /api/v1/map/events` | SSE: полный `snapshot`, затем `vehicle_updated`, `prediction_updated`, `incident_updated` |
| `GET /health` | Версия каталога/потока и количество ТС, прогнозов и инцидентов |

`route_pattern_id` — технический ID восстановленной геометрии, а не официальный номер московского маршрута. При совпадении времени с расписанием backend возвращает `matched`; при проверке live-потока вне исторического календаря — явно отличимый `matched_spatial`. Состояния `no_schedule`, `off_route`, `invalid_location` и `unmapped_unit` передаются без выдуманного маршрута, а frontend переводит технические коды в понятные оператору подписи: «Идёт по маршруту», «Вне маршрута», «Нет расписания», «ТС не привязано» и другие.

Статический каталог передаётся при инициализации. Координаты, скорость, курс, свежесть, найденный паттерн и соседние остановки обновляются потоково. Frontend отвечает только за отображение и локальные фильтры.

На карте и в списке транспорта работают общие фильтры:

- все ТС / идущие по маршруту / не находящиеся на маршруте;
- все / с задержкой / без задержки.

`currentDelaySeconds` появляется только после подтверждённого двумя пакетами перехода на следующий сегмент: backend сравнивает время прохождения остановки с её плановым временем. До этого отсутствие значения не трактуется как нулевая задержка.

ML получает только телеметрию с `event_time <= T` и первую остановку с плановым прибытием в `(T+10 минут, T+15 минут]`. Вызовы одного ТС ограничены шагом 5 минут его device-time. Текущий ответ ML содержит только прогноз в секундах, поэтому frontend не показывает выдуманные confidence, причину или версию модели.

Инцидент создаётся при прогнозе строго больше 120 секунд, обновляется для той же пары `unit_id + target_action_item_id` и закрывается, когда прогноз становится не больше порога либо окно переключается на следующую цель. Состояние хранится в памяти backend и очищается после перезапуска.

## Детерминированные mock-сценарии

В [backend/data/mock_scenarios.json](./backend/data/mock_scenarios.json) лежат сценарии длинного открытия дверей, пробки, плохого GPS, отклонения от маршрута, долгой стоянки, накопленного отставания и контрольного случая без сильного отклонения. Значения задержки ограничены диапазоном `-900..+900` секунд; все сценарии сохраняют рабочий горизонт прогноза 10–15 минут. Данные воспроизводимы и не зависят от случайной генерации официального эмулятора.

Это **тестовый контракт диспетчеризации**, не обучающая выборка: endpoint принимает готовую mock-величину прогноза и числовые свидетельства, после чего backend применяет прозрачные диагностические правила. Такой результат нельзя считать предсказанием ML или доказанной причиной реального опоздания. Для обучения и производственной диагностики нужны реальные размеченные наблюдения; в частности, официальный эмулятор не предоставляет надёжной длительности открытия дверей.

Локально поднять моковый Compose и загрузить пакет сценариев:

```powershell
docker compose --profile mock up --build -d
curl.exe -X POST http://localhost:8080/api/v1/demo/scenarios `
  -H "Content-Type: application/json" `
  --data-binary "@backend/data/mock_scenarios.json"
curl.exe http://localhost:8080/api/v1/dashboard/snapshot
```

В ответе endpoint проверяет ожидаемые коды причин и публикует прогнозы/инциденты в обычный snapshot и SSE. У инцидентов доступны `reasonCode`, `reason`, `evidence` и `scenarioId`; очередь frontend показывает объяснение и помечает тестовый сценарий. Вне локального Compose запустить backend с тестовым приёмом можно явно через `-enable-mock-scenarios`; не включайте этот неаутентифицированный demo endpoint в публичном окружении.

```bash
docker build --target build -t mt_predictor-backend-test ./backend
docker run --rm mt_predictor-backend-test \
  sh -c 'cd /src && go test ./... && go vet ./...'

docker compose build frontend

  sh -c 'npm run lint && npm test && npm run build'

  python -m unittest discover -s tests -v
```

```bash
curl http://localhost:8080/health
curl http://localhost:8080/api/v1/map/snapshot
curl http://localhost:8080/api/v1/dashboard/snapshot
curl -N http://localhost:8080/api/v1/map/events
```

## Текущие ограничения

- официальные публичные номера и названия маршрутов в раздаче отсутствуют;
- официальный случайный эмулятор использует неизвестные `unit_id`, поэтому доказывает ingestion, но не создаёт маршрутные прогнозы; профиль `historical-replay` отдельно воспроизводит исходную валидационную выборку и может содержать большие значения отклонения;
- часть линий имеет качество `stops_only`: между остановками нет подтверждённой GPS-геометрии;
- confidence и причина отсутствуют в текущем gRPC-ответе;
- действия диспетчера, постоянная история инцидентов и What-if в этот срез намеренно не входят.
