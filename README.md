# MT Predictor

Текущий интеграционный срез — рабочая диспетчерская карта без инцидентов и операторских сценариев. Backend принимает бинарный NDTP-поток, связывает `unit_id` с вычисленным паттерном маршрута, определяет соседние остановки и передаёт статический каталог и live-состояние транспорта в React-клиент.

## Быстрый запуск

Требуются Docker Desktop / Docker Engine с Compose и исходный датасет в `../../dataset` относительно репозитория. Весь демонстрационный контур запускается одной командой:

```bash
cd mt_predictor
./demo/start-demo.sh
```

После запуска:

- карта: <http://localhost:5173>;
- health backend: <http://localhost:8080/health>;
- HTTP/SSE API: `localhost:8080`;
- TCP-приёмник NDTP: `localhost:9201`.

Остановить контур:

```bash
docker compose --profile official-emulator down
```

По умолчанию контейнер `feeder` читает реальные траектории из `dataset/validate/traffic.csv`, кодирует строки обратно в бинарные NDTP-пакеты и отправляет их в тот же TCP listener, который принимает официальный эмулятор. Это не отдельный путь загрузки данных: декодирование, map matching и live-выдача у обоих источников общие.

## Что запускается

```text
traffic.csv -> NDTP feeder --TCP:9201--┐
                                      ├-> NDTP decoder -> map matching
официальный эмулятор --TCP:9201-------┘                         |
                                                                v
React + Leaflet <- snapshot + SSE <- HTTP API:8080 <- live state
```

- `backend` загружает вычисленный каталог маршрутов один раз при старте, слушает NDTP и публикует API карты;
- `feeder` воспроизводит восемь наиболее полных реальных треков с ускорением `50x` и зацикливает их;
- `frontend` показывает географическую карту OpenStreetMap, линии маршрутов, остановки и движущиеся маркеры ТС;
- синтетические train-примеры не попадают в каталог live-карты.

Плитки OpenStreetMap загружаются из интернета. Без сети сохраняются маршруты, остановки и транспорт, но не базовая подложка.

## Что делает единая команда

```bash
./demo/start-demo.sh
```

Скрипт при необходимости сам загружает образ организаторов, запускает все четыре контейнера, без вывода временных ошибок ждёт готовности Spring API и передаёт конфигурацию пяти тестовых ТС.

Если официальный эмулятор не нужен, базовый контур с воспроизведением CSV запускается отдельно:

```bash
docker compose up --build
```

## Ручной запуск официального эмулятора

Образ организаторов лежит вне репозитория и сначала загружается вручную:

```bash
docker load -i ../../dataset/ndtp-telemetry-emulator.tar
docker compose --profile official-emulator up -d official-emulator
curl -X POST http://localhost:18080/api/config \
  -H 'Content-Type: application/json' \
  --data-binary @demo/official-emulator-config.json
```

Пример запускает пять ТС (`990000101`, `990000307`, `990000509`, `990000711`, `990000913`) с `autoGenerate: true`. Для каждого ТС официальный эмулятор независимо генерирует случайную телеметрию и раз в секунду отправляет её в `backend:9201`. Выделенный числовой диапазон позволяет сразу отличить тестовые ТС, не добавляя в NDTP несуществующее строковое имя. Последние три цифры специально различаются, чтобы алгоритм `autoGenerate` разносил стартовые позиции по области, а не создавал все пять ТС рядом. Эти ID намеренно отсутствуют в каталоге раздачи, поэтому backend честно помечает их как «ТС не привязано». На Apple Silicon официальный образ запускается через эмуляцию `linux/amd64`, поэтому первый старт занимает несколько секунд.

Если официальный эмулятор запускается отдельной командой Docker, а backend — на хосте, в конфигурации следует использовать `targetHost: "host.docker.internal"`.

## Контракты карты

| Ресурс | Назначение |
|---|---|
| `GET /api/v1/map/init` | Статические остановки, геометрии route pattern, рейсы и реальные привязки `unit_id -> tr_id` |
| `GET /api/v1/map/snapshot` | Последнее согласованное состояние всех принятых ТС |
| `GET /api/v1/map/events` | SSE: начальный `snapshot`, затем события `vehicle_updated` |
| `GET /health` | Версия каталога, версия потока и количество ТС |

`route_pattern_id` — технический ID восстановленной геометрии, а не официальный номер московского маршрута. При совпадении времени с расписанием backend возвращает `matched`; при проверке live-потока вне исторического календаря — явно отличимый `matched_spatial`. Состояния `no_schedule`, `off_route`, `invalid_location` и `unmapped_unit` передаются без выдуманного маршрута, а frontend переводит технические коды в понятные оператору подписи: «Идёт по маршруту», «Вне маршрута», «Нет расписания», «ТС не привязано» и другие.

Статический каталог передаётся при инициализации. Координаты, скорость, курс, свежесть, найденный паттерн и соседние остановки обновляются потоково. Frontend отвечает только за отображение и локальные фильтры.

На карте и в списке транспорта работают общие фильтры:

- все ТС / идущие по маршруту / не находящиеся на маршруте;
- все / с задержкой / без задержки.

Текущий backend ещё не рассчитывает `currentDelaySeconds`. Поэтому интерфейс явно показывает «Данные задержки пока не поступают», а фильтры по задержке не принимают отсутствие данных за нулевую задержку. Они начнут работать без изменения UI после появления этого поля в live-состоянии ТС.

docker build --target build -t mt_predictor-backend-test ./backend
docker run --rm mt_predictor-backend-test \
  sh -c 'cd /src && go test ./... && go vet ./...'

docker compose build frontend
docker compose run --rm frontend \
  sh -c 'npm run lint && npm test && npm run build'

```bash
curl http://localhost:8080/health
curl http://localhost:8080/api/v1/map/snapshot
curl -N http://localhost:8080/api/v1/map/events
```

## Текущие ограничения

- официальные публичные номера и названия маршрутов в раздаче отсутствуют;
- календарь расписания исторический, поэтому текущий live-demo использует отдельно помеченный spatial fallback;
- часть линий имеет качество `stops_only`: между остановками нет подтверждённой GPS-геометрии;
- прогноз задержки, инциденты, реакции диспетчера и What-if в этот срез намеренно не входят.
