# MT Predictor

Текущий интеграционный срез объединяет диспетчерскую карту, постоянный жизненный цикл инцидентов, диагностику их возможных причин и обратную связь диспетчера. Backend принимает бинарный NDTP-поток, связывает `unit_id` с вычисленным паттерном маршрута, рассчитывает задержку и вызывает ML по gRPC. Инциденты и сообщения диспетчера сохраняются в PostgreSQL.

## Три сценария запуска

Для всех сценариев нужны Docker Desktop / Docker Engine с Compose. Команды выполняются из корня mt_predictor. Перед переключением режима остановите предыдущий источник телеметрии:

    docker compose --profile mock --profile official-emulator down

После запуска доступны frontend на http://localhost:5173, backend на http://localhost:8080, NDTP-приёмник на localhost:9201 и ML gRPC на localhost:50051.

### 1. Данные из исходного датасета

По умолчанию ожидается структура MSK/Project/mt_predictor и MSK/dataset: скрипт читает ../../dataset/validate/traffic.csv. Другой каталог можно передать через переменную DATASET_DIR. Feeder выбирает восемь наиболее полных траекторий, сохраняет исходную временную шкалу, кодирует строки в бинарные NDTP-пакеты и воспроизводит их с ускорением 5x.

    docker compose up -d --build postgres ml backend frontend feeder

Телеметрия проходит штатные decode, map matching, сопоставление с расписанием и реальный ML-прогноз. Расширенных полей дверей и дорожной обстановки в исходном CSV нет, поэтому диагностика использует только доступные признаки.

### 2. Официальный эмулятор NDTP

Этот режим проверяет приём живых бинарных пакетов от образа организаторов:

    docker load -i ../../dataset/ndtp-telemetry-emulator.tar
    docker compose up -d --build postgres ml backend frontend
    docker compose --profile official-emulator up -d official-emulator
    curl -X POST http://localhost:18080/api/config -H "Content-Type: application/json" --data-binary @demo/official-emulator-config.json

Эмулятор создаёт пять тестовых ТС из диапазона 990000xxx и отправляет пакеты раз в секунду. Эти ID отсутствуют в расписании, поэтому режим проверяет ingestion и live-карту, но обычно не создаёт маршрутные ML-прогнозы. Обычный feeder одновременно запускать не следует.

### 3. Mock-данные с обогащённой телеметрией

Это демонстрационный режим для ML-инцидентов и вычисления причин. Он воспроизводит пять движущихся фрагментов реальных маршрутов и передаёт синхронизированные признаки дверей, скорости, стоянки, загруженности, качества GPS и отклонения от маршрута.

    ./demo/start-demo.sh mock

Эквивалентный ручной запуск:

    docker compose --profile mock up -d --build postgres ml backend frontend mock-feeder
    curl -X POST http://localhost:8080/api/v1/demo/scenarios -H "Content-Type: application/json" --data-binary @backend/data/mock_scenarios.json

mock_telemetry.csv отвечает за движение пяти ТС, а mock_scenarios.json — за синхронизированные телематические признаки и расписания. Задержку прогнозирует реальный ML-сервис; причина и числовые подтверждения вычисляются backend-правилами из телеметрии, а не подставляются frontend. Набор демонстрирует длительное открытие дверей, дорожное замедление, отклонение от маршрута, длительную стоянку и отставание от расписания.

Проверка без браузера:

    curl http://localhost:8080/health
    curl http://localhost:8080/api/v1/dashboard/snapshot

## Быстрый запуск

Требуются Docker Desktop / Docker Engine с Compose и исходный датасет в родительской папке репозитория (`../train`, `../validate`, `../labels`). Весь демонстрационный контур запускается одной командой:

```bash
cd mt_predictor
./demo/start-demo.sh
```

После запуска:

- карта: <http://localhost:5173>;
- health backend: <http://localhost:8080/health>;
- HTTP/SSE API: `localhost:8080`;
- TCP-приёмник NDTP: `localhost:9201`.
- gRPC ML: `localhost:50051`.

Остановить контур:

```bash
docker compose --profile official-emulator down
```

По умолчанию контейнер `feeder` читает реальные траектории из `dataset/validate/traffic.csv`, сохраняет исходный `event_time`, кодирует строки обратно в бинарные NDTP-пакеты и отправляет их в тот же TCP listener, который принимает официальный эмулятор. Историческое время требуется, чтобы demo-телеметрия совпадала с календарём расписания и могла честно сформировать ML-цель. Это не отдельный путь загрузки данных: декодирование, map matching и live-выдача у обоих источников общие.

## Что запускается

```text
traffic.csv -> NDTP feeder --TCP:9201--┐
                                      ├-> decode -> map matching -> cur_dev_s
официальный эмулятор --TCP:9201-------┘                         |
                                                                v
React <- HTTP + SSE <- predictions/incidents <- gRPC -> ML ONNX
```

- `backend` загружает вычисленный каталог маршрутов один раз при старте, слушает NDTP, асинхронно вызывает ML и публикует API карты и инцидентов;
- `ml` загружает CatBoost + Transformer и использует FP32 ONNX Runtime для Transformer-части на CPU;
- `feeder` воспроизводит восемь наиболее полных реальных треков с ускорением `5x`;
- `frontend` показывает географическую карту и отдельную вкладку активных инцидентов;
- `postgres` постоянно хранит текущие, ожидающие и завершённые инциденты;
- синтетические train-примеры не попадают в каталог live-карты.

Плитки OpenStreetMap загружаются из интернета. Без сети сохраняются маршруты, остановки и транспорт, но не базовая подложка.

## Что делает единая команда

```bash
./demo/start-demo.sh
```

Скрипт при необходимости сам загружает образ организаторов, запускает все четыре контейнера, без вывода временных ошибок ждёт готовности Spring API и передаёт конфигурацию пяти тестовых ТС.

Если официальный эмулятор не нужен, базовый контур с воспроизведением CSV запускается отдельно:

```bash
docker compose up --build
```

## Ручной запуск официального эмулятора

Образ организаторов лежит вне репозитория и сначала загружается вручную:

```bash
docker load -i ../ndtp-telemetry-emulator.tar
docker compose --profile official-emulator up -d official-emulator
curl -X POST http://localhost:18080/api/config \
  -H 'Content-Type: application/json' \
  --data-binary @demo/official-emulator-config.json
```

Пример запускает пять ТС (`990000101`, `990000307`, `990000509`, `990000711`, `990000913`) с `autoGenerate: true`. Для каждого ТС официальный эмулятор независимо генерирует случайную телеметрию и раз в секунду отправляет её в `backend:9201`. Выделенный числовой диапазон позволяет сразу отличить тестовые ТС, не добавляя в NDTP несуществующее строковое имя. Последние три цифры специально различаются, чтобы алгоритм `autoGenerate` разносил стартовые позиции по области, а не создавал все пять ТС рядом. Эти ID намеренно отсутствуют в каталоге раздачи, поэтому backend честно помечает их как «ТС не привязано». На Apple Silicon официальный образ запускается через эмуляцию `linux/amd64`, поэтому первый старт занимает несколько секунд.

Если официальный эмулятор запускается отдельной командой Docker, а backend — на хосте, в конфигурации следует использовать `targetHost: "host.docker.internal"`.

## Контракты карты

| Ресурс | Назначение |
|---|---|
| `GET /api/v1/map/init` | Статические остановки, геометрии route pattern, рейсы и реальные привязки `unit_id -> tr_id` |
| `GET /api/v1/map/snapshot` | Последнее согласованное состояние всех принятых ТС |
| `GET /api/v1/dashboard/snapshot` | Согласованный снимок ТС, последних прогнозов и активных инцидентов |
| `GET /api/v1/map/events` | SSE: полный `snapshot`, затем `vehicle_updated`, `prediction_updated`, `incident_updated` |
| `GET /api/v1/incidents/history` | История с фильтром результата и серверной пагинацией |
| `GET /api/v1/incidents/{id}` | Карточка инцидента любого состояния |
| `GET /api/v1/incidents/{id}/actions` | Допустимые реакции и история сообщений диспетчера |
| `POST /api/v1/incidents/{id}/actions` | Поставить сообщение диспетчера в очередь отправки |
| `GET /health` | Версия каталога/потока и количество ТС, прогнозов и инцидентов |

`route_pattern_id` — внутренний ID восстановленной геометрии, а не официальный номер московского маршрута. Backend дополняет каталог консервативно сопоставленными номерами и названиями из публичного GTFS-снимка Москвы; неоднозначные совпадения остаются «Маршрут не определён». Повторные проходы одинакового контура с одним найденным номером объединяются в интерфейсе и не выдаются за разные маршруты. Названия остановок также берутся из публичного справочника по близости координат, а при отсутствии надёжного совпадения показывается «Название остановки неизвестно».

Исходный справочник и дата снимка записаны в `backend/data/generated/public_transport_reference.json`. Служебные `route_pattern_id`, `tr_id`, `unit_id` и хешированные ID остановок остаются во внутренних API для связи данных, но не показываются оператору. При совпадении времени с расписанием backend возвращает `matched`; при проверке live-потока вне исторического календаря — явно отличимый `matched_spatial`. Состояния `no_schedule`, `off_route`, `invalid_location` и `unmapped_unit` переводятся frontend в понятные подписи.

Статический каталог передаётся при инициализации. Координаты, скорость, курс, свежесть, найденный паттерн и соседние остановки обновляются потоково. Frontend отвечает только за отображение и локальные фильтры.

На карте и в списке транспорта работают общие фильтры:

- все ТС / идущие по маршруту / не находящиеся на маршруте;
- все / с задержкой / без задержки.

`currentDelaySeconds` появляется только после подтверждённого двумя пакетами перехода на следующий сегмент: backend сравнивает время прохождения остановки с её плановым временем. До этого отсутствие значения не трактуется как нулевая задержка.

ML получает только телеметрию с `event_time <= T` и первую остановку с плановым прибытием в `(T+10 минут, T+15 минут]`. Вызовы одного ТС ограничены шагом 5 минут его device-time. Текущий ответ ML содержит только прогноз в секундах, поэтому frontend не показывает выдуманные confidence, причину или версию модели.

Инцидент создаётся при прогнозе строго больше 120 секунд. При смене цели он ожидает фактического прохождения остановки; после подтверждения двумя пакетами на следующем сегменте PostgreSQL сохраняет фактическое отклонение и результат. Если свежий прогноз той же цели снижается до порога, инцидент снимается. Незавершённые записи восстанавливаются после перезапуска.

Для активного или ожидающего инцидента backend возвращает допустимые реакции с учётом причины. Нажатие в карточке создаёт запись operator_actions, связанную с инцидентом, ТС и маршрутом. Адресат разделяет сообщения водителю и диспетчерскому штабу, а статус pending делает таблицу outbox-очередью для будущего сервиса доставки. Отправленные реакции сразу отображаются в истории карточки и сохраняются после перезапуска.

## Текущие ограничения

- часть маршрутов невозможно однозначно сопоставить с публичным GTFS только по восстановленной геометрии, поэтому интерфейс честно помечает их как неопределённые;
- официальный случайный эмулятор использует неизвестные `unit_id`, поэтому доказывает ingestion, но не создаёт маршрутные прогнозы; ML-demo работает через CSV feeder с исходным временем;
- часть линий имеет качество `stops_only`: между остановками нет подтверждённой GPS-геометрии;
- confidence и причина отсутствуют непосредственно в текущем gRPC-ответе: причину рассчитывает backend по телематике;
- внешний сервис доставки сообщений пока не входит в проект: backend оставляет их в operator_actions со статусом pending;
- What-if моделирование в текущий срез не входит.
